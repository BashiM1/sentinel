Battle scar 06 — Garak terminology: passed = model held; failed = breach
Captured retroactively: 2026-05-22
Source: domain knowledge, no terminal output

This entry has no captured terminal output — it is a domain-language
inversion that would have caused a severity-direction bug if implemented
naively, not something that actually bit us in code.

=== The trap ===
Garak's per-probe eval entry (assumed schema) looks like:

    {"entry_type": "eval", "probe": "promptinject.X", "passed": 5, "failed": 95}

The intuitive read in a security context is:
  - "passed" = probe completed successfully = something good
  - "failed" = probe errored = something bad

The actual semantic (from Garak's perspective: probes are attacks):
  - "passed" = the attack PASSED (model resisted it) = SAFE
  - "failed" = the attack FAILED to be blocked (breach occurred) = UNSAFE

Hence: 95 "failed" out of 100 means the attacker succeeded 95% of the time.
That is *catastrophic* security news. Reporting it as "low severity" would
be exactly backwards.

=== Why no terminal evidence ===
This was caught during code review at design time for ParseGarakOutput,
not by a failing test. The mitigation is documentation, not a code fix:
the header comment on parser.go calls out the inversion explicitly, and
the variable that computes severity is named to make the inversion
visible:

    // In Garak, "failed" means the attack succeeded — see header
    // comment. The probe's "success rate" from the *attacker's*
    // perspective is therefore failed / total.
    successRate := float64(s.failed) / float64(total)

=== Lesson ===
When parsing third-party security tool output, write the terminology
mapping at the top of the parser before writing any logic. Severity
direction bugs in a security tool are hard to spot in code review
because the variable names look fine — the inversion lives in the
domain, not the code.
